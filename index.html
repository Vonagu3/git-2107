Конспект занятия 8: история и cherry-pick

Что показывали на занятии — по шагам, чтобы повторить самим в «Копилке» (istoriya-igra, как скачать — вкладка «Практика», шаг 0). Ответов детектива здесь нет: примеры другие. Выход из git log и git blame — клавиша q.

1. Как читать граф

git log --oneline --graph --all
  • Каждая строка — коммит: хеш (хватит первых 7 символов) и сообщение. Сверху — самые новые.
  • В скобках — ярлыки веток: (main), (moya-vetka). Ярлык стоит на последнем коммите ветки и сам переезжает вперёд при каждом новом коммите в ней.
  • HEAD -> main — вы сейчас в ветке main. Это не про незакоммиченные изменения: их показывает git status.
  • Коммит, сделанный после данного, — его потомок, предыдущий — родитель. Развилка |/ появляется там, где у коммита двое потомков: от него пошли две ветки. Пока в новой ветке нет своих коммитов, развилки не видно — ярлыки просто стоят на одном коммите.
git log --oneline --graph main moya-vetka

Только две ветки: видно, от какого коммита moya-vetka отошла от main и насколько main ушёл вперёд.

2. Что было в файле

git log --oneline README.md
git log -p README.md

Первая — только коммиты, где менялся README, вторая — и сами изменения: строки с - — как было, с + — как стало. Например, видно, как цель сменилась с наушников на велосипед.

git show 83f1651
git show --stat b0611b4

git show — один коммит целиком: кто, когда, зачем и что поменял. --stat — только список файлов.

3. В каком коммите появилось слово

git log -S "def trati" --oneline

→ один коммит «Посчитал траты». -S ищет коммиты, где слово появилось или исчезло. Кавычки нужны, если в слове пробел. Коммиты одного человека: git log --oneline --author="Аня".

4. Кто последним менял строку: git blame

git blame README.md

Каждая строка подписана слева направо: хеш коммита → автор → дата → номер строки → сама строка. Значок ^ перед хешем — строка с самого первого коммита.

git blame -L 5,5 README.md
git show 83f1651
git blame -L 5,5 README.md 83f1651~1
  • -L 5,5 — только строка 5 (-L 5,10 — с 5 по 10).
  • Blame говорит кто и когда, а зачем — в самом коммите: git show ХЕШ.
  • ХЕШ~1 — коммит перед этим. Так видно, какой строка была раньше: «Цель: накопить на наушники». Можно идти назад по одной строке, как по следам.

Без терминала. GitHub: открыть файл → кнопка Blame над текстом, рядом History — все коммиты файла. VS Code: панель Timeline внизу слева в Explorer — история открытого файла.

Зачем blame. Не чтобы ругать, а чтобы знать, у кого спросить. Нашли в проекте странную строку → blame → пишете автору в issue или в Telegram.

5. Cherry-pick: взять один коммит из другой ветки

Ситуация. В ветке ispravlenie черновик и исправление опечатки в README. Ветка не готова, а исправление нужно в main сейчас.
git log --oneline -3 origin/ispravlenie
git checkout main
git cherry-pick ХЕШ
git log --oneline -3
  • Это копия: у коммита в main новый хеш, в ветке остался старый. Черновик не приехал — только один коммит.
  • Похоже на патч с занятия 7: патч — недописанные правки между людьми, cherry-pick — готовый коммит между ветками.
  • Конфликт — решаете как обычно, затем git add и git cherry-pick --continue. Передумали — git cherry-pick --abort.
  • В репозитории команды main защищён, поэтому так: git checkout -b fix-imya от main → cherry-pick → push → pull request. Это часть 4 домашки.
Merge и rebase не успели и пока отложили. Задание В на вкладке «Практика» (раздел «Для повторения · занятие 8») можно попробовать самим, но не обязательно.

Практика на занятии 9: сайт проекта на GitHub Pages

Командой, в репозитории проекта команды. У каждой команды будет сайт по адресу логин-владельца.github.io/название-репозитория/ — его можно показать жюри конференции. Страницы — обычные .md из папки docs/ в main, поэтому меняем их как любой файл: ветка → pull request → review. Отмечайте шаги галочками — они запомнятся в этом браузере.

Кто есть кто. Участник 1 — владелец репозитория, 2 и 3 — остальные, как в домашке. Круг review: PR Участника 1 проверяет 2, PR 2 — 3, PR 3 — 1.

Для повторения · занятие 8: история, blame, cherry-pick, rebase

Каждый сам, в учебном репозитории «Копилка» — маленькой программе на Python, которую писали четверо: Аня, Боря, Вика и Гоша. Работаем только у себя: push не делаем, у вас нет на это прав, так и задумано. Отмечайте шаги галочками — они запомнятся в этом браузере.

0. Скачать · 3 минуты

А. Детектив · 12 минут

Ответы на 5 вопросов пришлите руководителю в личку, не в общий чат.

  1. Кто написал функцию samaya_bolshaya_trata?

    git log -S "def samaya_bolshaya_trata" --oneline

    -S ищет коммиты, где это слово появилось или исчезло. Автора покажет git show ХЕШ.

  2. Кто последним поменял в kopilka.py строку return (ostatok + v_nedelyu - 1) // v_nedelyu и в каком коммите?

    git blame kopilka.py

    Каждая строка подписана: хеш коммита, автор, дата, номер строки. Значок ^ перед хешем — строка с самого первого коммита. Номер строки виден и в VS Code слева от текста. То же на GitHub: откройте kopilka.py → кнопка Blame.

  3. Как раньше называлась переменная ostatok и кто написал ту, старую строку?

    git blame -L НОМЕР,НОМЕР kopilka.py ХЕШ~1

    -L 20,20 — только строка 20: вместо НОМЕР — номер строки из вопроса 2. ХЕШ — из ответа на вопрос 2, ~1 — «коммит перед ним». Убираете -L — убирайте и числа. Другой способ: git show ХЕШ и смотреть строки с - и +.

  4. Какие файлы поменял коммит «Операции из файла»?

    git log --oneline
git show --stat ХЕШ

  5. Сколько коммитов сделал Боря?

    git log --oneline --author="Боря"

Б. Cherry-pick: взять один коммит · 10 минут

Ситуация. Вика в ветке ispravlenie начала черновик и попутно исправила опечатку в README — «капилка». Ветка не готова, а исправление нужно в main прямо сейчас. Берём один коммит, а не всю ветку.

  1. Найти коммит

    git log --oneline -3 origin/ispravlenie

    Скопируйте хеш коммита «Исправил опечатку в README».

  2. Перенести в main

    git checkout main
git cherry-pick ХЕШ
git log --oneline -3

    В main новый коммит с тем же сообщением, но другим хешем — это копия. В README теперь «копилка», а файла velosiped.md нет: черновик остался в ветке Вики.

В. Rebase: моя ветка поверх свежего main · 20 минут

Зачем. Ветку создали давно, а main ушёл вперёд. git pull origin main добавил бы merge-коммит. git rebase main делает иначе: снимает ваши коммиты, обновляет основу и кладёт их сверху заново. История получается прямой, а коммиты — переписанными, с новыми хешами.

  1. Без конфликта

    git checkout moya-vetka
git log --oneline --graph -10 --all
git rebase main
git log --oneline --graph -6

    До — ветка отходит от старого main. После — три коммита «Идея: …» сверху, хеши у них новые.

  2. С конфликтом

    git checkout konflikt
git rebase main

    CONFLICT в README.md: эту же строку «Цель» поменяли и в main, и в ветке. Откройте README в VS Code. При rebase всё наоборот: сверху (HEAD, Current) — main, снизу (Incoming) — ваш коммит. Читайте текст, а не кнопки.

    Оставьте одну строку Цель: … — какую хотите, хоть свою, — уберите метки <<<<<<< ======= >>>>>>>, сохраните.

    git add README.md
git rebase --continue
git log --oneline --graph -6

    После --continue откроется сообщение коммита — просто закройте вкладку (Vim: Esc, :wq, Enter). Запутались — git rebase --abort, всё вернётся как было, и заново.

  3. Убрать за собой

    git checkout main
git reset --hard origin/main
git status

    Main снова как на GitHub. Папку istoriya-igra потом можно удалить. Напишите в чат группы «готово».

Правило rebase. Только в своей ветке, в которой не работает никто другой. В main и общих ветках — никогда. После rebase обычный git push откажет: на GitHub старые коммиты, у вас новые. Тогда git push --force-with-lease — и только в своей ветке. Approve в pull request после этого сбросится, ревьюер посмотрит ещё раз.

Для повторения · занятие 7: карман git stash и патч-файл

Часть 1 — каждый сам: прячем недописанную работу в карман и достаём обратно. Часть 2 — в паре, если останется время: передаём недописанные правки напарнику файлом. Всё в папке репозитория своей команды. Push не делаем. Отмечайте шаги галочками — они запомнятся в этом браузере.

Зачем. Вы дописываете README в своей ветке, остановились на середине. Пишет напарник: «глянь мой PR». Коммитить полуготовое не хочется — прячем в карман: git stash.

1. Каждый сам: карман git stash · 10 минут

  1. Подготовка

    Откройте в VS Code папку репозитория своей команды.

    git status

    Если там не nothing to commit — напишите в чат группы, прежде чем идти дальше.

    git checkout main
git pull
git checkout -b proba-imya

    Вместо imya — своё имя латиницей.

  2. Коммит в ветке

    Допишите строку в конец README.md, сохраните.

    git add README.md
git commit -m "Проба stash"

    Теперь README в вашей ветке не такой, как в main.

  3. Карман

    Допишите ещё одну строку в README.md, сохраните. Не коммитьте.

    git checkout main

    Какая ошибка? Git не пускает: недописанное пропало бы. Он сам подсказывает — закоммитить или спрятать.

    git stash
git status

    Чисто? Строка из файла пропала?

    git checkout main
git checkout proba-imya
git stash list
git stash pop

    Теперь пустило. В кармане лежала одна запись, после pop строка вернулась в файл.

  4. Новый файл

    Создайте файл test.txt с любым текстом.

    git stash

    Что пишет? Новые файлы, которые git ещё не отслеживает, сами в карман не попадают. Для них ключ -u — «и новые файлы тоже».

    git stash -u
git stash pop
rm test.txt
git status

    После -u файл исчез, после pop вернулся, после rm удалён насовсем. test.txt больше нет в списке. Осторожно: rm удаляет файл с диска, незакоммиченный уже не вернуть.

  5. Убрать за собой

    git restore README.md
git status
git checkout main
git branch -D proba-imya

    Должно быть nothing to commit, working tree clean. Большая -D — потому что коммит «Проба stash» не слит в main. Напишите в чат группы «готово».

Привычка. Если файл в обеих ветках одинаковый, git пускает в другую ветку без ошибки, и недописанное переезжает с вами. Перед git commit смотрите git status: первая строка — On branch ….

2. В паре: патч-файл · 7 минут, если останется время

stash — карман на вашем компьютере. Патч — тот же карман, но файлом: его можно отправить напарнику или перенести со школьного компьютера домой.

  1. Владелец: сохранить правки в файл

    git checkout main
git pull

    Допишите строку в конец README.md, сохраните. Не коммитьте.

    git diff --output=../my.patch
git restore README.md

    В терминале ничего не выведется — так и должно быть. Файл my.patch появился рядом с папкой репозитория. git restore — только после --output, иначе патч будет пустым. Отправьте my.patch напарнику в личку Telegram.

  2. Напарник: применить

    git checkout main
git pull

    Положите my.patch в папку над репозиторием — рядом с ним, не внутрь.

    git apply --check ../my.patch
git apply ../my.patch
git diff

    После --check тишина — значит, ляжет. В git diff строка напарника. Скрин — в чат группы.

  3. Оба: убрать за собой

    git restore README.md
rm ../my.patch

    Напишите в чат группы «готово».

Сохраняйте патч только через git diff --output=…, а не git diff > my.patch: в Windows PowerShell > портит файл. В патче весь текст правок — с паролем или токеном его не отправляем. И патч не заменяет pull request: настоящая работа идёт через ветку и PR.

Для повторения · занятия 5–6: от задачи до слияния

Что делаем на занятии после показа руководителя. Сначала владелец включает правила ветки main. Часть 1 — вдвоём в репозитории своей пары: ставите друг другу задачи, делаете pull request, просите доработать и сливаете. Часть 2 — каждый сам: учимся отменять изменения и коммиты. Часть 3 — каждый сам: исправляем историю, когда push уже был. Отмечайте шаги галочками — они запомнятся в этом браузере.

Главное правило. Задача → своя ветка → pull request → review напарника → слияние. Сливает автор, и только после Approve.

Сначала: правила ветки main · 5 минут

Делает владелец репозитория, один раз. Напарник смотрит его экран. После этого GitHub сам не даст слить pull request без Approve напарника и с нерешёнными замечаниями.

Имена в репозитории уже должны быть вписаны и отправлены (миссия 0): после включения правила прямой git push в main перестанет работать — только через pull request.

  1. Открыть создание правила

    В репозитории пары на GitHub: Settings → Rules → Rulesets → New ruleset → New branch ruleset.

  2. Назвать и включить

    Ruleset name: main

    Enforcement status: выберите Active.

    Bypass list не трогайте, он должен остаться пустым: иначе владелец сможет сливать в обход правила.

  3. Выбрать ветку

    Target branches → Add target → Include default branch. Так правило относится к ветке main.

  4. Поставить три галочки

    Найдите и включите Require a pull request before merging. Внутри откроются настройки:

    • Required approvals: 1 — нужен один Approve;
    • Dismiss stale pull request approvals when new commits are pushed — после нового коммита Approve нужно получить заново;
    • Require conversation resolution before merging — все замечания должны быть отмечены Resolve conversation.

    Остальное не меняйте. Внизу страницы Create.

  5. Проверить

    В списке Rulesets появилась строка main со статусом Active.

    Если вверху жёлтая плашка «Your rulesets won't be enforced on this private repository» — правило сохранено, но GitHub его не применяет: в закрытом репозитории на бесплатном тарифе правила не действуют, только в публичном. Скажите руководителю и идите дальше: тогда «сливаем только после Approve» остаётся договорённостью пары.

Как понять, что правило работает: в открытом pull request внизу написано Review required и Merging is blocked, кнопка Merge серая, пока напарник не поставит Approve.

1. В паре: идея проекта через задачу · 35 минут

Каждый пишет в идея.md свою идею проекта. Но не просто так: напарник ставит вам задачу, вы делаете её в своей ветке, напарник проверяет и просит доработать.

У пары ещё нет репозитория? Сначала миссия 0 на странице шаблона: github.com/Vonagu3/praktika-shablon — и напишите руководителю.

  1. Поставить задачу напарнику

    На GitHub в репозитории пары: вкладка Issues → New issue.

    Название: Идея проекта: ИМЯ НАПАРНИКА

    Описание — список из трёх пунктов:

    - [ ] Что делаем и для кого
- [ ] Какие данные нужны и откуда
- [ ] Первый шаг

    Справа Assignees → выберите напарника. Нажмите Create.

    В итоге задач две. Найдите ту, где ответственный — вы, и запомните её номер: он стоит после названия, например #3.

  2. Сделать свою задачу в ветке

    git checkout main
git pull
git checkout -b идея-имя

    В идея.md заполните три строки в своём разделе, сохраните.

    git add .
git commit -m "Идея: имя"
git push -u origin идея-имя

  3. Открыть pull request и привязать задачу

    На GitHub: жёлтая плашка Compare & pull request. Плашки нет — Pull requests → New pull request → compare: ваша ветка.

    В описании напишите одну строку со своим номером задачи:

    Closes #3

    Create pull request. Справа в блоке Development должна появиться ваша задача. Сами не сливаете.

  4. Проверить pull request напарника

    Откройте PR напарника → Files changed. Читайте как человек со стороны:

    • понятно, для кого проект?
    • понятно, откуда взять данные?
    • первый шаг можно сделать за неделю?

    Владелец репозитория обязательно просит доработать. Наведите на строку → синий + → напишите, что уточнить. Затем Review changes (или Submit review), в поле — список:

    Доработать:
- [ ] что именно поправить

    Выберите Request changes → Submit review.

    Второй участник: всё понятно — Approve, непонятно — тоже Request changes.

    Замечание пишите так, чтобы по нему можно было сделать: не «переделай», а «напиши, где возьмёшь данные о погоде».

  5. Доработать и слить

    Вас попросили доработать — исправляете в той же ветке, новый PR не нужен:

    git add .
git commit -m "Идея: доработал по замечаниям"
git push

    В своём PR: у каждого комментария Resolve conversation. Справа Reviewers → круглая стрелка рядом с напарником: «посмотри ещё раз».

    Напарник: Approve. Автор: Merge pull request → Confirm merge.

  6. Проверить, что всё закрылось

    • Issues → Closed: две задачи. Их никто не закрывал руками — это сделало Closes.
    • Pull requests → Closed: два слитых PR с идеями.
    • Хотя бы в одном PR есть красный значок Changes requested.

    Оба обновляют main у себя:

    git checkout main
git pull

Закончили раньше? Сделайте тем же способом миссию 3: задача напарнику «Вопрос по git: имя», ветка вопросы-имя, файл вопросы.md.

2. Каждый сам: тренировка отмены · 10 минут

В папке репозитория пары, в ветке, которая никуда не сливается. Push здесь не делаем.

git checkout main
git pull
git checkout -b проба-имя

  1. Вернуть испорченный файл

    Сотрите пару строк в визитка.md, сохраните.

    git status
git restore визитка.md

    Файл стал как был. Осторожно: то, что вы напечатали, пропадает насовсем.

  2. Убрать лишний файл из коммита

    Создайте файл лишний.txt, напишите в нём что угодно.

    git add .
git status
git restore --staged лишний.txt
git status

    Файл стал красным: он на месте, но в коммит не пойдёт. Удалите его.

  3. Исправить сообщение коммита

    Допишите строку в конец визитка.md, сохраните.

    git add .
git commit -m "Проба с опечаткйо"
git commit --amend -m "Проба"
git log --oneline -3

    Коммит один, сообщение новое.

  4. Убрать коммит целиком

    git reset --hard HEAD~1
git log --oneline -3

    Коммита «Проба» нет, строки в файле тоже.

  5. Удалить пробную ветку

    git checkout main
git branch -D проба-имя

    Напишите в чат группы «готово».

3. Каждый сам: исправляем историю после push · 25 минут

Теперь то же самое, но ошибка уже на GitHub. В каждом шаге вы сами делаете ошибку, смотрите на неё на GitHub, исправляете и смотрите, что изменилось. Всё происходит в пробной ветке, которая никуда не сливается, pull request не открываем.

В настоящей работе сначала отвечают на два вопроса — от них зависит способ:

ВопросОтветЧто делать
Ветка уже слита в main?ДаИсторию не трогаем, отменяем сверху: шаг 7
НетСмотрите следующий вопрос
В ветке работает кто-то кроме вас?ДаШаг 7 или сначала договориться с напарником
Нет, ветка только вашаМожно переписать: шаги 2–5
Переписать историю значит заменить коммиты на GitHub другими. Обычный git push этого не даст, нужен git push --force-with-lease. Он безопаснее, чем --force: откажется, если на GitHub появились чужие коммиты, которых у вас нет.

  1. Подготовить пробную ветку и отправить её

    git checkout main
git pull
git checkout -b отмена-имя

    Создайте файл проба.txt, напишите в нём первая строка, сохраните.

    git add .
git commit -m "Проба: первый коммит"
git push -u origin отмена-имя

    Где смотреть на GitHub. На странице репозитория нажмите кнопку с названием ветки main и выберите отмена-имя. Справа над списком файлов ссылка Commits — это история ветки. Сверху ваш коммит «Проба», ниже — коммиты из main, их не считаем. Оставьте вкладку открытой: после каждого шага обновляйте её.

  2. Опечатка в сообщении коммита

    Ошибаемся. Допишите в проба.txt строку вторая строка, сохраните.

    git add .
git commit -m "Проба: втарой коммит"
git push

    Обновите Commits на GitHub: коммит с опечаткой уже там. Запомните его номер справа — семь букв и цифр.

    Исправляем.

    git commit --amend -m "Проба: второй коммит"
git status

    git status пишет have diverged и советует git pull. Так и должно быть: у вас новый коммит, на GitHub старый. Pull не делаем — он вернёт коммит с опечаткой в ветку.

    git push --force-with-lease

    Смотрим. На GitHub коммитов «Проба» по-прежнему два, сообщение исправлено, а номер коммита другой: это новый коммит на месте старого.

  3. Ошибка в файле в последнем коммите

    Ошибаемся. Допишите строку третья строка с ошибкай, сохраните.

    git add .
git commit -m "Проба: третий коммит"
git push

    Исправляем. Поправьте слово в файле, сохраните. Добавляем исправление в тот же коммит:

    git add .
git commit --amend --no-edit
git show HEAD
git push --force-with-lease

    --no-edit оставляет старое сообщение. git show HEAD показывает, что теперь в коммите: строка без ошибки. Если вывод длинный и внизу двоеточие — нажмите q.

    Смотрим. На GitHub откройте третий коммит: в нём сразу правильная строка, будто ошибки не было.

  4. Лишний коммит целиком

    Ошибаемся. Создайте файл лишний.txt, напишите что угодно, сохраните.

    git add .
git commit -m "Лишний коммит"
git push

    На GitHub сверху появился «Лишний коммит», в ветке — файл лишний.txt.

    Исправляем.

    git reset --hard HEAD~1
git log --oneline -4
git push --force-with-lease

    Смотрим. Файл пропал из папки, на GitHub нет ни «Лишнего коммита», ни лишний.txt: сверху снова «Проба: третий коммит».

    Если работа из коммита ещё нужна, вместо --hard пишут --soft: коммит исчезнет, а файл останется.

  5. Пароль в коммите, после которого есть другие

    Ошибаемся. Допишите в проба.txt строку пароль: 12345, сохраните.

    git add .
git commit -m "Проба: настройки"

    Допишите ещё строку четвёртая строка, сохраните.

    git add .
git commit -m "Проба: четвёртый коммит"
git push

    Пробуем исправить «в лоб». Сотрите строку с паролем, сохраните.

    git add .
git commit -m "Проба: убрал пароль"
git push

    На GitHub откройте файл проба.txt: пароля нет. Теперь откройте Commits → коммит Проба: настройки: пароль на месте, зелёной строкой. Новый коммит сверху ничего не стёр.

    Исправляем по-настоящему. --amend не подойдёт: он правит только последний коммит. Найдите коммит перед тем, где появился пароль, — это «Проба: третий коммит» — и скопируйте его номер из первой колонки:

    git log --oneline -6

    Разбираем три верхних коммита обратно на изменения (вместо НОМЕР — скопированный номер):

    git reset --soft НОМЕР
git status

    проба.txt зелёный: коммиты пропали, а файл остался таким, как вы его сохранили, — с четвёртой строкой и без пароля. Собираем один новый коммит:

    git commit -m "Проба: четвёртый коммит"
git push --force-with-lease

    Смотрим. На GitHub четыре коммита «Проба» — с первого по четвёртый. «Проба: настройки» и «Проба: убрал пароль» исчезли, пароля нет ни в одном.

    С настоящим паролем или токеном первым делом заменяют его на новый там, где его выдали: всё, что побывало на GitHub, считается украденным. Старый коммит ещё долго открывается по прямой ссылке, даже когда в ветке его уже нет.

  6. Отменили не то: вернуть через журнал

    Ошибаемся. Убираем последний коммит, как будто по ошибке:

    git reset --hard HEAD~1
git log --oneline -3

    Четвёртого коммита нет, четвёртой строки в файле тоже.

    Исправляем. Git записывает каждое перемещение по истории. Этот журнал есть только на вашем компьютере:

    git reflog -5

    Верхняя строка — где вы сейчас, вторая, HEAD@{1}, — где были до последней команды. Возвращаемся на одно действие назад:

    git reset --hard "HEAD@{1}"
git log --oneline -3

    Смотрим. Коммит и строка в файле вернулись. Push не нужен: на GitHub ничего не менялось.

    Возвращать нужно тоже с --hard: с --soft коммит вернётся, а файл останется без строки. И не вернётся то, что ни разу не было в коммите.

  7. Отменить без переписывания: revert

    Так поступают, когда ветка уже слита в main или в ней работает напарник: у других эти коммиты уже есть, заменять их нельзя.

    git revert HEAD --no-edit
git log --oneline -3
git push

    Смотрим. Обычный git push прошёл без --force-with-lease. На GitHub «Проба: четвёртый коммит» остался, а сверху появился Revert "Проба: четвёртый коммит", который убирает четвёртую строку. История не переписана, а дополнена.

    Для уже слитого pull request то же самое делает кнопка Revert на его странице: GitHub сам откроет новый PR с отменой.

  8. Убрать за собой

    git checkout main
git branch -D отмена-имя
git push origin --delete отмена-имя

    Последняя команда удаляет ветку на GitHub. Напишите в чат группы «готово».

В настоящей ветке после переписывания

  • Открытый pull request обновится сам. Approve напарника сбросится — попросите посмотреть ещё раз.
  • Если напарник успел скачать вашу ветку, у него осталась старая история. Он выполняет у себя (вместо ветка — имя ветки): 
    git fetch
git checkout ветка
git reset --hard origin/ветка
  • Переписать main не получится: правило ветки отклонит такой push. В main только шаг 7.

Cherry-pick: взять один коммит из черновика · 25 минут · каждый свой

  
Ситуация. Вы начали в ветке черновик, а попутно нашли и исправили ошибку в своём документе. Черновик не готов, а исправление нужно в main сейчас. Берём один коммит. Main защищён, поэтому так: новая ветка от main → cherry-pick → pull request.

  
    
    
  1. Задача
    
      
    Issue «Исправление в docs/… — Имя». Assignees — себя, метка документация, справа Projects → доска команды. В описании:
    
      
    Что сделать: исправить ошибку в docs/ВАШ_ФАЙЛ.md без черновика.
Зачем: исправление нужно в main сейчас, черновик ещё не готов.
Готово, когда:
- [ ] в main исправление есть
- [ ] файла chernovik-imya.md в main нет
    
    
    2. 
    
  2. Ветка-черновик с двумя коммитами
    
      
    git checkout main
git pull
git checkout -b chernovik-imya
    
      
    Вместо imya — своё имя латиницей. Исправьте в своём документе ошибку или неточность, сохраните:
    
      
    git add .
git commit -m "Исправил ошибку в docs/ВАШ_ФАЙЛ.md"
    
      
    Теперь черновик: создайте файл chernovik-imya.md с любой недописанной идеей для проекта, сохраните:
    
      
    git add .
git commit -m "Черновик: идея"
git log --oneline -3
    
      
    Скопируйте хеш коммита «Исправил ошибку…» — он второй сверху.
    
    
    3. 
    
  3. Взять только исправление
    
      
    git checkout main
git checkout -b fix-imya
git cherry-pick ХЕШ
git log --oneline -3
    
      
    В ветке fix-imya новый коммит с тем же сообщением, но другим хешем — это копия. Файла chernovik-imya.md в папке нет: черновик остался в своей ветке.
    
    
    4. 
    
  4. Pull request и уборка
    
      
    git push -u origin fix-imya
    
      
    Pull request с Closes #номер, review по кругу: ревьюер проверяет, что в Files changed только исправление и нет черновика. Approve → Merge. Черновик на GitHub не отправляли — удалите ветку у себя:
    
      
    git checkout main
git pull
git branch -D chernovik-imya
