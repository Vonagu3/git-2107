# Занятие 17 — основы API на примере Supabase

120 минут, включая перерыв 5 минут. Каждый отправляет HTTP-запросы в Postman к своей учебной базе; проверка результатов — в парах. Программирование не требуется.

Главная идея: раньше мы работали с базой через SQL, теперь обращаемся к её данным из другого приложения через API.

Материалы: [Практика](Практика.md) — ученикам; [Ответы](Ответы.md), [Подготовка Supabase](Подготовка_Supabase.md) и [коллекция Postman](Урок_17.postman_collection.json) — преподавателю. Ученики собирают запросы сами; коллекцию решений открываем после попытки.

## Откуда продолжаем

На занятии 16 работали с `users`, `chats`, `chat_members`, `invitations`: ограничениями и `alter table`. Домашка добавляла роль «модератор» и назначала её Сове в «Общем». Сегодня используем отдельную учебную копию этой модели с уже выполненной домашкой. Существующие базы прошлого урока сохраняем.

В API сначала читаем знакомые таблицы, затем создаём одного нового пользователя. Авторизацию пользователей, SDK, соединения таблиц через API и написание сервера оставляем на следующие занятия. RLS объясняем как правила доступа; каждый ученик заранее применяет готовый стартовый SQL в своём проекте, преподаватель проверяет готовность.

## Результат занятия

Ученик умеет:

- Объяснить, что такое API, клиент, сервер, запрос и ответ.
- Найти в запросе метод, URL, параметры, заголовки и тело.
- Прочитать простой JSON, статус ответа и сообщение об ошибке.
- Получить, создать, изменить и удалить запись через API Supabase.
- Объяснить, почему ограничения базы действуют и при обращении через API.

## Подготовить до урока

1. Пройти [инструкцию подготовки](Подготовка_Supabase.md) на демонстрационном проекте. Каждый ученик заранее готовит свой проект по разделу «Настройка Postman» в практике: запускает стартовый SQL, берёт адрес и publishable key из своей панели и проверяет доступ через API.
2. Установить и открыть Postman Desktop на ученических компьютерах. Проверить сеть и импорт [шаблона окружения](Урок_17.postman_environment.json).
3. Подготовить собственный демонстрационный проект. В каждом проекте должны быть 4 пользователя, 3 чата, 4 участия и 4 приглашения.
4. Прогнать коллекцию преподавателя на демонстрационном проекте по порядку. Проверить, что после опытов пользователь `100` удалён, а исходные строки сохранены.
5. Раздать «Практику». На случай проблем с сетью использовать примеры ответов из «Ответов»; самостоятельную отправку запросов тогда перенести в домашку.

## 0–10 — связь с прошлым уроком

За 5 минут разобрать домашку: у Совы роль «модератор» в «Общем», «администратор» в «Играх». Почему роль лежит в `chat_members`, а не в `users`? Почему роль «главный» по-прежнему запрещена?

Поставить задачу: «В приложении открыли список чатов. Пользователь SQL не пишет. Как приложение получает данные?» Собрать предположения; в конце урока вернуться к ним.

## 10–25 — что такое API

API — согласованный способ, которым одна программа обращается к возможностям другой. HTTP API — один из видов API. API не обязательно связан с базой: можно запросить прогноз погоды или отправить сообщение.

На доске нарисовать:

```text
Postman (клиент) → HTTP-запрос → API Supabase → PostgreSQL
Postman (клиент) ← HTTP-ответ  ← API Supabase ← результат
```

Клиент инициирует обращение; сервер принимает его и обрабатывает по правилам. На нашем уроке Postman выполняет роль приложения. Supabase предоставляет PostgreSQL и готовый API к данным; мы не пишем сервер с нуля. [Документация Data API](https://supabase.com/docs/guides/api).

Вопросы классу: «Кто здесь клиент? Где хранятся строки? Что вернётся, если записи нет? Может ли приложение запросить любые данные без разрешения?»

## 25–40 — устройство HTTP

Разобрать пример из ученического листа: `GET /rest/v1/users?select=id,nickname&id=eq.1`.

- Метод говорит, какую операцию просит выполнить клиент.
- URL содержит адрес сервера, путь к ресурсу и параметры после `?`.
- Заголовки передают дополнительную информацию: ключ приложения, формат тела.
- Тело передаёт данные, например нового пользователя. В наших `GET` тела нет.
- Ответ содержит статус, заголовки и, когда предусмотрено, тело.

Показать JSON с одним объектом внутри массива. Разобрать `{}`, `[]`, двойные кавычки, строку, число и `null`. Отличить число `1` от строки `"1"`; показать, почему лишняя запятая делает JSON некорректным.

Сопоставить `GET` с чтением, `POST` с созданием, `PATCH` с изменением полей, `DELETE` с удалением. Это операции сегодняшнего REST API, а не правило для любого API. `eq.` и `select` — синтаксис Supabase/PostgREST, не язык HTTP и не SQL.

## 40–55 — первый запрос вместе

По разделу «Настройка Postman» в практике создать окружение и запрос. Сначала получить всех пользователей, затем выбрать `id,nickname`, затем оставить пользователя `1`.

Каждый показывает статус, тело ответа и место, где задан фильтр. Спросить: «Почему результат — массив, хотя найден один пользователь?» Запрос возвращает список подходящих строк; он может содержать одну строку или быть пустым.

Если у ученика ошибка доступа, проверить URL и `apikey`; не подменять ключ на административный. Не задерживать весь класс: предложить временно работать в паре за одним компьютером.

## 60–75 — самостоятельное чтение

Задания П1–П3 из практики: все чаты, один чат, участия в чате `10`. До отправки ученик записывает ожидаемое число строк, после — объясняет фильтр соседу.

На сверке П3 обратить внимание: вернулись номера пользователей и роли, а не ники. API возвращает запрошенные поля; связи сами по себе не подставляют имена.

## 75–95 — полный цикл изменения

Создать пользователя `100` с ником «Рысь», прочитать его, изменить ник на «Барс», прочитать снова, удалить и подтвердить отсутствие. Первую вставку показать вместе, остальные шаги ученики выполняют по заданиям И2–И6.

На запросах с JSON добавить `Content-Type: application/json`, на изменениях — `Prefer: return=representation`, чтобы видеть изменённые строки. Без этой настройки успешный ответ может быть без тела. [Возврат данных в PostgREST](https://docs.postgrest.org/en/stable/references/api/preferences.html#return-representation).

Перед `PATCH` и `DELETE` попросить показать фильтр `id=eq.100`. Обсудить аналогию с `where`: без фильтра запрос может затронуть все доступные строки. Проверка результата через `GET` обязательна.

## 95–110 — ошибки и доступ

Опыты О1–О4: существующий `id`, пустой ник, неверный ключ, отсутствующий пользователь. Меняем только одно условие за раз. Для ошибки читаем статус и сообщение; затем объясняем, на каком этапе остановилась операция.

Обобщить: `2xx` — успех, `4xx` — проблема запроса или доступа, `5xx` — сбой на стороне сервера. `200` с `[]` — успешный запрос без видимых совпадений, а не обязательно поломка API.

Ключ приложения не обозначает вошедшего пользователя и не даёт автоматически все права. RLS ограничивает доступ к строкам. На уроке правила заранее настроены для вымышленных данных; пользователи приложения ещё не входят в аккаунты. Публичный клиентский ключ не заменяет правила доступа. [Ключи Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## 110–120 — итог и домашка

Самостоятельно получить участия пользователя `1`, вывести `chat_id,role`. Попросить объяснить метод, ресурс, фильтр и ответ. Ответ — две строки.

Устно: чем API отличается от базы; где передать фильтр, а где данные для создания; почему `PRIMARY KEY` действует через API; что значит пустой массив; почему ключ не заменяет права.

Домашка описана в практике: цикл работы с пользователем `101`, отчёт о запросах и одна намеренная ошибка. Критерий успеха — ученик составляет запрос и объясняет ответ, после удаления подтверждает отсутствие записи.

Если группа отстаёт, сократить самостоятельное чтение до П1 и П3. Сохранить цикл изменения и разбор ошибок. Не тратить практику на установку инструментов или подробный синтаксис RLS.
