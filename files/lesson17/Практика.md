# Занятие 17 — обращаемся к базе через API

Сегодня Postman будет нашим приложением: отправит запросы в Supabase и покажет ответы. Работаем со знакомыми пользователями и чатами в отдельной учебной базе. SQL для выполнения заданий не нужен.

`users` здесь — наша учебная таблица. Создание строки с ником не регистрирует аккаунт Supabase и не позволяет войти в приложение: вход пользователей будем разбирать отдельно.

Перед отправкой каждого запроса запишите прогноз. После отправки сохраните метод, путь с параметрами, тело запроса, статус и результат. Ключ в отчёт не включайте.

## Настройка Postman

1. Откройте Postman Desktop. Импортируйте выданный [шаблон окружения](Урок_17.postman_environment.json) через Import.
2. В Environments откройте «Урок 17 — мой учебный проект». Заполните `base_url` адресом проекта вида `https://ВАШ-ПРОЕКТ.supabase.co` без `/` в конце, а `publishable_key` — выданным преподавателем ключом. Выберите это окружение активным.
3. Создайте коллекцию «Мои запросы — урок 17», а в ней HTTP-запрос. Для Authorization выберите No Auth: на уроке ключ передаётся отдельным заголовком.
4. Выберите метод `GET`, введите `{{base_url}}/rest/v1/users`.
5. На вкладке Headers добавьте строку: Key — `apikey`, Value — `{{publishable_key}}`. Не вставляйте ключ в URL или тело.
6. Нажмите Send. Найдите статус ответа и тело. Если переменные не подставились, проверьте выбранное окружение и сохранённые значения.

Сохраняйте запросы в коллекцию. При создании следующего запроса можно дублировать предыдущий, но проверяйте метод, адрес, Headers и Body. Для `GET` и `DELETE` выбирайте Body → none.

## Шпаргалка

| Часть запроса | Пример | Назначение |
|---|---|---|
| Метод | `GET` | Что хотим сделать |
| Адрес сервера | `{{base_url}}` | К какому проекту обращаемся |
| Путь | `/rest/v1/users` | С каким ресурсом работаем |
| Параметры | `select=id,nickname&id=eq.1` | Какие поля и строки нужны |
| Заголовок | `apikey: {{publishable_key}}` | Ключ приложения |
| Тело | `{"id":100,"nickname":"Рысь"}` | Данные для создания записи |

Параметры можно вводить во вкладке Params отдельными строками. Postman сам добавит `?` и `&` в URL. Не дублируйте один параметр одновременно вручную и через Params.

| Задача в нашем API | Метод | Аналог в SQL |
|---|---|---|
| Получить данные | `GET` | `SELECT` |
| Создать строку | `POST` | `INSERT` |
| Изменить поля | `PATCH` | `UPDATE` |
| Удалить строку | `DELETE` | `DELETE` |

`select=id,nickname` выбирает столбцы. `id=eq.1` означает «id равен 1». `order=id.asc` сортирует по возрастанию `id`. Это правила API Supabase/PostgREST; у других API параметры могут называться иначе.

JSON передаёт данные. Объект записывается в `{}`, массив — в `[]`. Имена полей и строки заключаются в двойные кавычки, числа — без кавычек. `null` означает отсутствие значения. После последнего поля запятую не ставят.

## Первый запрос вместе

1. Получите всех пользователей: `GET {{base_url}}/rest/v1/users`.
2. Во вкладке Params добавьте `select` со значением `id,nickname` и `order` со значением `id.asc`.
3. Добавьте параметр `id` со значением `eq.1`.
4. Найдите в ответе массив, объект, число и строку. Сколько строк осталось? Где в запросе это задано?

У ответа есть статус, заголовки и тело. Например, `200 OK` сообщает об успехе, а JSON в теле содержит результат. Статус — не поле внутри JSON.

## Практика 1 — получаем данные

В каждом запросе сохраняйте заголовок `apikey`. В П1–П3 добавьте сортировку по `id`, чтобы удобнее сверять ответы.

**П1. Все чаты.** Получите `id` и `name` всех чатов. Сколько строк ожидаете?

**П2. Один чат.** Получите те же поля только для чата `10`. Как изменились параметры?

**П3. Участники чата.** Обратитесь к `chat_members`. Получите `user_id,role` только для чата `10`. Не перепутайте номер участия `id` и номер чата `chat_id`. Почему в ответе нет ников?

## Практика 2 — создаём, изменяем и удаляем

Используем нового пользователя с `id=100`. В этой базе `id` нужно задавать явно. После каждого изменения проверяйте состояние отдельным `GET`.

Для запросов с телом откройте Body → raw → JSON. Проверьте заголовок `Content-Type: application/json`. На `POST`, `PATCH` и `DELETE` добавьте `Prefer: return=representation`, чтобы сервер вернул затронутые строки. Заголовок `apikey` нужен во всех запросах.

### И1. Создать пользователя вместе

Метод: `POST`. URL: `{{base_url}}/rest/v1/users`. Уберите параметры от предыдущих запросов.

```json
{"id": 100, "nickname": "Рысь"}
```

Отправьте один раз. Сохраните статус и тело ответа. Что произойдёт, если повторить тот же запрос?

### И2. Проверить создание

Составьте `GET`, который вернёт `id,nickname` только пользователя `100`. Тело запроса не требуется.

### И3. Изменить ник

Метод: `PATCH`. Ресурс: `users`. Добавьте фильтр по `id=100`. В теле передайте только поле `nickname` со значением «Барс».

Перед Send покажите соседу фильтр. Какие строки мог бы затронуть запрос без него?

### И4. Проверить изменение

Повторите запрос И2. Убедитесь, что номер пользователя остался прежним, а ник изменился.

### И5. Удалить пользователя

Метод: `DELETE`. Ресурс: `users`. Оставьте фильтр по пользователю `100`. Body → none. Сохраните ответ: это данные удалённой строки, а не доказательство, что она осталась в базе.

### И6. Проверить удаление

Повторите запрос И2. Какой статус и какое тело вернулись? Успешно ли выполнен запрос?

## Практика 3 — объясняем ошибки

Меняйте одно условие за раз. Не исправляйте ограничения базы ради успешного запроса. После неудачной вставки убедитесь через `GET`, что исходные данные не изменились.

**О1. Повтор номера.** Отправьте `POST` в `users` с телом `{"id":1,"nickname":"Дубликат"}`. Найдите статус, `code` и `message`. Какое правило сработало? Проверьте, что у пользователя `1` сохранился ник «Лис».

**О2. Пустой ник.** Отправьте `POST` с телом `{"id":102,"nickname":""}`. Почему новый `id` не помогает? Убедитесь, что пользователь `102` не появился.

**О3. Неверный ключ.** Дублируйте рабочий `GET`. Только в копии замените значение заголовка `apikey` на `invalid-key-for-lesson`. Саму переменную окружения не меняйте. Отправьте копию, затем повторите исходный запрос. Чем ошибка доступа отличается от ошибки ограничения?

**О4. Нет подходящей строки.** С правильным ключом запросите пользователя `999`. Сравните статус и тело с О3. Пустой список и отказ в доступе — один и тот же результат?

Классы статусов: `2xx` — успех, `4xx` — проблема запроса или доступа, `5xx` — сбой на стороне сервера. Не угадывайте причину только по первой цифре: читайте сообщение.
