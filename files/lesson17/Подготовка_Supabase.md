# Подготовка Supabase и Postman к уроку 17

Инструкция преподавателю. Подготовьте свой демонстрационный проект. Каждый ученик самостоятельно готовит отдельный учебный проект в своём аккаунте Supabase и берёт его адрес и publishable key из своей панели. До урока дайте ссылку на раздел «Настройка Postman» в [практике](Практика.md) и проверьте готовность проектов. При проверке в парах каждый отправляет запросы в свою базу.

## Учебная база

1. Эти шаги преподаватель выполняет в своём демонстрационном проекте, а каждый ученик — в своём отдельном учебном проекте Supabase. Не используйте проект с реальными пользователями или данными. На уроке разрешена работа без входа в аккаунт приложения.
2. В SQL Editor выполните целиком [supabase_setup.sql](supabase_setup.sql). Скрипт создаёт четыре таблицы, ограничения, вымышленные строки, права и политики RLS в одной транзакции. Если любое из четырёх имён уже занято, он остановится без изменения данных. Не удаляйте старые таблицы ради запуска: выберите пустой проект. При ручной работе в сессии с прерванной транзакцией сначала выполните `rollback;`.
3. Проверьте итог: `users` — 4, `chats` — 3, `chat_members` — 4, `invitations` — 4. В `chat_members.id=3` роль «модератор»; в `chats.id=10` описание «Общение участников».
4. В настройках проекта проверьте, что Data API включён, а схема `public` доступна через него. SQL-скрипт не переключает настройки сервиса.
5. Откройте Connect в своём проекте и скопируйте Project URL и publishable key. Ключ также доступен в Settings → API Keys. Адрес и ключ должны относиться к одному проекту. Нужен ключ вида `sb_publishable_…`, не secret key и не `service_role`. Используем только заголовок `apikey`; Authorization в Postman — No Auth.

Скрипт подготавливает состояние после занятия 16 и домашки про модераторов. Он не зависит от исполнения предыдущих SQL-файлов и не меняет базы прошлых занятий.

`public.users` — учебная таблица, не таблица `auth.users` сервиса Supabase Auth. Никаких аккаунтов через неё мы не создаём.

## Доступ в этом упражнении

| Таблица | Чтение через API | Создание, изменение, удаление через API |
|---|---|---|
| `users` | Разрешено | Разрешено |
| `chats` | Разрешено | Запрещено |
| `chat_members` | Разрешено | Запрещено |
| `invitations` | Разрешено | Запрещено |

RLS включён на всех четырёх таблицах. Права и политики заданы для роли `anon`: так обращается учебный клиент с publishable key без пользовательской сессии. Права на таблицу разрешают операцию, а политика RLS определяет доступные строки. SQL Editor обычно работает с более широкими правами, поэтому успешный SQL ещё не проверяет доступ ученика через API.

Открытые политики `users` позволяют любому обладателю клиентского ключа этого проекта менять все учебные строки. Это условие изолированного упражнения, не модель доступа для реального приложения. После проверки домашки каждый владелец выключает Data API у своего выделенного учебного проекта, если он больше не нужен для практики. [RLS в Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Postman преподавателя

1. Используйте Postman Desktop, чтобы не тратить занятие на настройку браузерного агента. Проверьте отправку запросов на ученических компьютерах до урока.
2. Импортируйте [окружение](Урок_17.postman_environment.json) и [коллекцию решений](Урок_17.postman_collection.json).
3. В окружении заполните `base_url` адресом проекта без завершающего `/`, а `publishable_key` — клиентским ключом. Выберите окружение активным. В поставленных файлах значения пустые.
4. Откройте первый запрос и отправьте его вручную. Должны вернуться четыре пользователя со статусом `200`.
5. На своём демонстрационном проекте выполните запросы коллекции по порядку. Раздел «Изменения» создаёт пользователя `100`, переименовывает и удаляет его. Раздел «Ошибки» содержит намеренно неудачные запросы; неверный ключ задан только у одного запроса, окружение не изменяется.
6. В конце выполните «К1. Исходные пользователи»: должны остаться только Лис, Сова, Кот и Волк с номерами `1–4`. Повтор полного цикла возможен после завершённого удаления `100`. Если предыдущий запуск оборвался, сначала проверьте наличие `100` и завершите его удаление отдельным запросом И5.

Коллекция содержит сохранённые примеры ответов для разбора без сети. Это учебные примеры ожидаемого поведения, не записи обращения к конкретному облачному проекту. Для полной предпроверки используйте Runner с одной итерацией: проверки статусов, тел и ошибок должны пройти. Скрипты проверок только читают ответы, не отправляют дополнительных запросов и не меняют переменные.

Ученикам выдайте «Практику» и пустой шаблон окружения. Готовую коллекцию решений используйте после самостоятельной попытки. Не публикуйте экспорт окружения с заполненными ключами вместе с отчётами учеников.

## Если запрос не работает

| Симптом | Что проверить |
|---|---|
| В URL осталось `{{base_url}}` | Выбрано ли окружение и заполнено ли значение |
| Нет HTTP-ответа, ошибка соединения | Доступность сети и проекта; правильность URL |
| `401` или сообщение о неверном ключе | Заголовок `apikey`, соответствие ключа проекту, отсутствие лишнего Authorization |
| Таблица не найдена | Data API включён, `public` доступна, скрипт выполнен успешно; после создания таблиц повторить запрос через несколько секунд |
| `200` и `[]`, хотя строка видна в SQL Editor | Фильтр и проект, права роли `anon`, SELECT-политика RLS |
| `400` с `23514` при пустом нике | Ожидаемая ошибка CHECK, не проблема подключения |
| `409` с `23505` при создании `100` | Запись уже существует; выяснить, на каком шаге остановились |
| Изменение успешно, но тело пустое | Заголовок `Prefer: return=representation`; проверить результат отдельным GET |

Не исправляйте доступ заменой клиентского ключа на административный или отключением RLS. Сверьте настройки с SQL-скриптом. Если сеть недоступна, используйте примеры ответов в коллекции и [ответах](Ответы.md); отправку запросов ученики выполнят позже.

## Проверка материалов

Локально проверено на PostgreSQL 15 и PostgREST 13.0.7: запуск SQL, отказ при повторном запуске без потери данных, включение RLS, 19 запросов коллекции от роли `anon`, запрет изменения трёх таблиц для чтения, ошибки NULL и некорректного JSON, сохранность исходных данных. Облачный шлюз Supabase и опыт О3 с неверным ключом в эту проверку не входят; их проверьте на учебном проекте перед занятием.
