# Занятие 17 — ответы преподавателю

Ученикам выдаём [практику](Практика.md). Здесь — решения, ожидаемые ответы и объяснения. Все URL ниже дополняются адресом проекта `{{base_url}}`. В каждом запросе нужен заголовок `apikey: {{publishable_key}}`. В Postman Authorization — No Auth; ключ не передаём как Bearer-токен.

Примеры рассчитаны на [стартовую базу](supabase_setup.sql). Это образцы ожидаемого поведения; работа конкретного проекта проверяется перед уроком по [инструкции](Подготовка_Supabase.md). Готовые запросы и сохранённые ответы также есть в [коллекции Postman](Урок_17.postman_collection.json).

## Домашка прошлого урока

Ограничение ролей теперь допускает «администратор», «участник», «модератор». В «Общем» Лис — администратор, Сова — модератор. В «Играх» Сова — администратор, Лис — участник. Роль зависит от конкретного участия, поэтому лежит в `chat_members`.

Для перехода от состояния урока 16 нужно удалить ограничение `chat_members_role_check`, создать его с расширенным набором ролей и изменить участие `id=3`. Роль «главный» запрещена по-прежнему. В новом стартовом скрипте эти изменения уже включены; на уроке 17 повторять ALTER TABLE не нужно.

## Первый запрос

```http
GET {{base_url}}/rest/v1/users?select=id,nickname&id=eq.1
apikey: {{publishable_key}}
```

Статус `200 OK`, тело:

```json
[{"id":1,"nickname":"Лис"}]
```

Это список из одного объекта. При снятии фильтра и добавлении `order=id.asc`:

```json
[
  {"id":1,"nickname":"Лис"},
  {"id":2,"nickname":"Сова"},
  {"id":3,"nickname":"Кот"},
  {"id":4,"nickname":"Волк"}
]
```

Без явной сортировки порядок строк не гарантирован. Пробелы и порядок полей JSON не меняют смысл ответа.

## Практика 1 — чтение

### П1. Все чаты

`GET /rest/v1/chats?select=id,name&order=id.asc` → `200`:

```json
[
  {"id":10,"name":"Общий"},
  {"id":11,"name":"Игры"},
  {"id":12,"name":"Новый чат"}
]
```

### П2. Один чат

`GET /rest/v1/chats?select=id,name&id=eq.10&order=id.asc` → `200`:

```json
[{"id":10,"name":"Общий"}]
```

### П3. Участники чата

`GET /rest/v1/chat_members?select=user_id,role&chat_id=eq.10&order=id.asc` → `200`:

```json
[
  {"user_id":1,"role":"администратор"},
  {"user_id":2,"role":"модератор"}
]
```

Фильтр относится к `chat_id`, а не к `id` участия. Ники хранятся в другой таблице и не были запрошены. Связи через FK не означают автоматическое включение всех связанных полей в ответ.

## Практика 2 — изменения

На `POST` и `PATCH` добавляем `Content-Type: application/json`. На `POST`, `PATCH`, `DELETE` — `Prefer: return=representation`. На всех запросах сохраняем `apikey`.

| Шаг | Метод и путь | Тело запроса | Статус | Тело ответа |
|---|---|---|---|---|
| И1 | `POST /rest/v1/users` | `{"id":100,"nickname":"Рысь"}` | `201 Created` | `[{"id":100,"nickname":"Рысь"}]` |
| И2 | `GET /rest/v1/users?select=id,nickname&id=eq.100` | Нет | `200 OK` | `[{"id":100,"nickname":"Рысь"}]` |
| И3 | `PATCH /rest/v1/users?id=eq.100` | `{"nickname":"Барс"}` | `200 OK` | `[{"id":100,"nickname":"Барс"}]` |
| И4 | Повтор И2 | Нет | `200 OK` | `[{"id":100,"nickname":"Барс"}]` |
| И5 | `DELETE /rest/v1/users?id=eq.100` | Нет | `200 OK` | `[{"id":100,"nickname":"Барс"}]` |
| И6 | Повтор И2 | Нет | `200 OK` | `[]` |

Повтор И1 после успешного создания даст конфликт первичного ключа. Повтор `GET` данные не меняет. После удаления повторный `DELETE` с тем же фильтром не найдёт строку; с нашим заголовком вернёт `200` и `[]`. Это не означает, что удаление не работает.

Без `Prefer: return=representation` по умолчанию тело изменения не возвращается: для `POST` обычно `201`, для `PATCH` и `DELETE` — `204`. Поэтому отсутствие JSON само по себе не означает ошибку. [Возврат представления в PostgREST](https://docs.postgrest.org/en/stable/references/api/preferences.html#return-representation).

Без фильтра `PATCH` или `DELETE` может затронуть все доступные строки таблицы. На наших данных удаление исходных пользователей ещё может встретить внешние ключи, но полагаться на это нельзя. Для демонстрации не отправляем массовые изменения: достаточно сопоставления с SQL без `where`.

## Практика 3 — ошибки

### О1. Повтор первичного ключа

`POST /rest/v1/users` с `{"id":1,"nickname":"Дубликат"}` → `409 Conflict`, `code` равен `23505`.

Пример тела:

```json
{
  "code":"23505",
  "details":"Key (id)=(1) already exists.",
  "hint":null,
  "message":"duplicate key value violates unique constraint \"users_pkey\""
}
```

Запись не заменяется: мы отправили обычное создание, а не обновление или upsert. Проверка `GET` по `id=1` возвращает «Лис».

### О2. Пустой ник

`POST /rest/v1/users` с `{"id":102,"nickname":""}` → `400 Bad Request`, `code` равен `23514`. Сообщение называет `users_nickname_not_empty`. Новый номер не отменяет проверку содержимого ника. После ошибки `GET` по `id=102` возвращает `[]`.

HTTP-статус `400` и PostgreSQL-код `23514` — разные уровни описания ошибки: статус показывает класс ответа, код уточняет нарушение CHECK. Формулировка `details` может различаться; важны причина и имя ограничения. [Соответствие ошибок и HTTP-статусов](https://docs.postgrest.org/en/stable/references/errors.html).

### О3. Неверный ключ

`GET /rest/v1/users?select=id,nickname&id=eq.1`, заголовок `apikey: invalid-key-for-lesson` → ожидается `401 Unauthorized` и сообщение о неверном API-ключе. Ответ шлюза может иметь другую структуру, чем ошибка PostgreSQL, например только поле `message`.

Запрос не получает доступ к таблице. После возвращения к исходному запросу с правильным ключом снова получаем `200` и Лиса. Не требовать дословного английского сообщения: это не ошибка ограничения и в нём не обязан быть PostgreSQL-код.

### О4. Нет совпадений

`GET /rest/v1/users?select=id,nickname&id=eq.999` с правильным ключом → `200 OK`, тело `[]`.

Ресурс `users` существует, запрос допустим, подходящих видимых строк нет. Это отличается от ошибки в адресе ресурса и от отказа из-за неверного ключа. При других политиках RLS пустой массив также может означать, что строки клиенту не видны; по одному `[]` нельзя доказать отсутствие строки во всей базе.

## Выходное задание

`GET /rest/v1/chat_members?select=chat_id,role&user_id=eq.1&order=id.asc` → `200`:

```json
[
  {"chat_id":10,"role":"администратор"},
  {"chat_id":11,"role":"участник"}
]
```

Засчитываем, если ученик верно выбрал `chat_members`, фильтрует по `user_id`, получает две строки и объясняет результат. Порядок параметров в URL значения не имеет.

## Ответы на итоговые вопросы

1. **API и база.** База хранит данные и проверяет их правила. API предоставляет операции, через которые программа может обратиться к данным или другим возможностям сервиса.
2. **Фильтр и новые данные.** В сегодняшнем API фильтр находится в параметрах URL; данные создания — в JSON-теле `POST`.
3. **Пустой массив.** Запрос мог выполниться успешно, но не найти доступных совпадений. Сначала смотрим статус, затем тело и условия запроса.
4. **Ограничения.** Запись через API в итоге обрабатывает PostgreSQL, поэтому PK, FK, NOT NULL и CHECK сохраняют силу.
5. **Ключ и права.** Publishable key относится к приложению, а не к конкретному вошедшему человеку. Права и RLS определяют, какие операции и строки доступны. Для входа пользователя потребовалась бы отдельная авторизация. [Ключи Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## Проверка домашки

Для пользователя `101` ожидаются: `201` и «Ёж», `200` и «Ёж», `200` и «Енот», повторное чтение «Енот», `200` с удалённой строкой, `200` с `[]`. В запросах изменения и удаления должен быть фильтр `id=eq.101`.

Намеренная ошибка: дубликат исходного `id` → `409` / `23505`; пустой ник с новым `id=103` → `400` / `23514`. Ошибка не должна менять исходные строки. Ученик объясняет причину своими словами и не включает ключ в отчёт.
